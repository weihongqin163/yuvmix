# MixYuv 四路 720p 合流性能测试

## 测试目的

分析四路 1280x720 I420 输入合成为一路 1280x720 I420 输出时，
`MixYuv` 内部各类操作的耗时占比，并定位主要性能热点。

测试场景与 `mix_yuv_four_source_test` 一致：

- 4 路 1280x720 I420 输入。
- 每路缩放至 640x360，按 2x2 布局合成到 1280x720 输出。
- 填充模式为 `contain`。
- 4 路分别绘制 `agora-yuv-1` 至 `agora-yuv-4`。
- 第一路启用高亮边框。
- 输出颜色采用 BT.709 limited range。

## 测试环境

- 操作系统：macOS。
- CPU 架构：arm64。
- 编译器：AppleClang 14.0.0。
- 性能构建：CMake `Release`，`-O3 -DNDEBUG`。
- 稳定态测试：每组先预热 10 次，再执行 1000 次并统计中位数。

本报告的绝对耗时仅代表上述测试环境。Linux x86_64 和 macOS x86_64
需要在目标机器上重新测试，但各操作的算法复杂度和热点位置不变。

## 优化前稳定态结果

| 操作 | 增量耗时 | 约占完整调用 |
| --- | ---: | ---: |
| 填充 1280x720 背景 | 约 0.03 ms | 约 3% |
| 4 路 I420 双线性缩放 | 约 0.10-0.11 ms | 约 11% |
| 绘制一路高亮边框 | 约 0.82 ms | 约 85% |
| 绘制 4 个显示名称 | 约 0.01 ms | 约 1% |
| 完整 `MixYuv` | 约 0.97 ms | 100% |

对照组的 Release 中位数如下：

| 对照组 | 中位耗时 |
| --- | ---: |
| 仅背景填充 | 约 0.03 ms |
| 背景填充 + 4 路缩放 | 约 0.13-0.14 ms |
| 背景填充 + 4 路缩放 + 高亮 | 约 0.95 ms |
| 背景填充 + 4 路缩放 + 文字 | 约 0.14-0.15 ms |
| 全部启用 | 约 0.97 ms |

各项增量耗时通过相邻对照组相减获得，因此可能存在约 0.01 ms 的测量波动。

## Y-only 高亮优化结果

新增的 `mix_yuv_benchmark` 使用相同四路输入、布局、高亮和 OSD 配置，执行
10 次预热后测量 1000 次调用并报告中位数。它不注册为 CTest，避免把机器相关的
时间阈值混入正确性测试。

同一台 macOS arm64 机器、同一套 Release 静态依赖构建的结果如下：

| 实现 | 完整 `MixYuv` 中位耗时 |
| --- | ---: |
| 优化前整帧 mask | 0.963-0.969 ms |
| 优化后 Y-only 四窄带 | 0.149 ms |

优化后 5 次独立运行的中位数分别为 0.162、0.149、0.149、0.145 和
0.149 ms。以 0.963 ms 与 0.149 ms 对比，完整合流耗时降低约 84.5%，
吞吐性能约提升 6.5 倍。结果达到本次优化设定的 0.30 ms 以下目标。

## 首次调用

以下首次调用数据来自优化前的整帧 mask 实现，用于保留历史基线。

稳定态测试会复用 `MixYuvContext`，字形和缓冲区已经进入缓存。测试用例中的
单次调用还可能包含以下首次执行成本：

- 高亮 mask 首次分配。
- FreeType 字形首次加载、栅格化和缓存。
- libyuv CPU 路径初始化。
- 指令页、字体文件和数据页的冷缓存开销。

Release 构建的新进程首次调用实测约为 1.28-3.71 ms，随后复用同一个 context
时稳定在约 0.97 ms。首次调用受操作系统页缓存和 CPU 状态影响较大。

Debug 构建曾测得 15.272 ms。该构建只有 `-g`，没有编译优化，不能用于评估
发布版本性能。

## 优化前热点分析

当前主要热点是 `DrawHighlights`。一路 640x360 高亮在 1280x720 输出上会执行：

1. 清空整个高亮 mask，共 921,600 个元素。
2. 遍历整个 640x360 高亮 Rect，共 230,400 个像素，判断像素是否位于边框。
3. 再扫描整个 Y plane，共 921,600 个像素，根据 mask 写入高亮颜色。
4. 再扫描 640x360 个 UV 位置，每个位置读取对应的 4 个 Y mask 值并计算覆盖率。

即使实际边框只有约 4 像素宽，高亮实现仍会对整个输出执行多轮标量扫描，
因此高亮约占完整调用耗时的 85%。

其他操作：

- 4 路缩放由 `libyuv::I420Scale` 完成。当前场景是 1280x720 到 640x360
  的精确二分之一缩放，libyuv 的 SIMD 路径耗时较低。
- FreeType 字形缓存在 `MixYuvContext` 中。稳定态主要执行少量字形位图的 Y plane
  混合，耗时约占 1%。
- 背景填充需要写入约 1.38 MB 的 I420 数据，但在 Release 下只占约 3%。

## 优化后的高亮路径

高亮现在只修改 Y plane，U/V plane 保持 source 合流后的原值。彩色高亮因此变为
亮度高亮，这是为最低 CPU 开销而明确接受的视觉取舍。

每个高亮 Rect 仍使用原有边框宽度、内外各半和输出边缘裁剪规则，但边框被拆成
上、下、左、右四条互不重叠的窄带。每条窄带逐行执行连续 `std::fill_n`：

1. 不再分配、清零或扫描输出尺寸的 mask。
2. 不再扫描完整 Y plane。
3. 不再扫描或混合 U/V plane。
4. 高亮工作量由输出面积改为与实际边框面积成正比。
5. 多个高亮重叠时只会重复写相同的 Y 常量，不需要并集或去重状态。

## 后续优化优先级

1. 高亮四窄带优化已经完成，不再是主要热点。
2. 如果布局可以证明完全覆盖输出，可考虑跳过会被后续 source 全部覆盖的背景填充。
   该项收益约为 3%，优先级较低。
3. 当前缩放和文字绘制不是主要瓶颈，不建议在没有新性能数据的情况下优先改动。

## 结论

四路 720p 合流在本机 Release 稳定态由约 0.97 ms 降至约 0.15 ms。高亮路径
不再执行整帧 mask 和 Y/UV 扫描，完整调用约提升 6.5 倍。该结果只代表上述
macOS arm64 环境；其他架构仍需使用同一 benchmark 独立测量。
