# MixYuv 四路 720p 合流性能测试

## 测试目的

分析四路 1280x720 I420 输入合成为一路 1280x720 I420 输出时，
`MixYuv` 内部各类操作的耗时占比，并定位主要性能热点。

测试场景与 `mix_yuv_four_source_test` 一致：

- 4 路 1280x720 I420 输入。
- 每路缩放至 640x360，按 2x2 布局合成到 1280x720 输出。
- 填充模式为 `contain`。
- 4 路分别绘制 `agora-yuv-1` 至 `agora-yuv-4`。
- 第一路启用高亮边框。
- 输出颜色采用 BT.709 limited range。

## 测试环境

- 操作系统：macOS。
- CPU 架构：arm64。
- 编译器：AppleClang 14.0.0。
- 性能构建：CMake `Release`，`-O3 -DNDEBUG`。
- 稳定态测试：每组先预热 10 次，再执行 1000 次并统计中位数。

本报告的绝对耗时仅代表上述测试环境。Linux x86_64 和 macOS x86_64
需要在目标机器上重新测试，但各操作的算法复杂度和热点位置不变。

## 优化前稳定态结果

| 操作 | 增量耗时 | 约占完整调用 |
| --- | ---: | ---: |
| 填充 1280x720 背景 | 约 0.03 ms | 约 3% |
| 4 路 I420 双线性缩放 | 约 0.10-0.11 ms | 约 11% |
| 绘制一路高亮边框 | 约 0.82 ms | 约 85% |
| 绘制 4 个显示名称 | 约 0.01 ms | 约 1% |
| 完整 `MixYuv` | 约 0.97 ms | 100% |

对照组的 Release 中位数如下：

| 对照组 | 中位耗时 |
| --- | ---: |
| 仅背景填充 | 约 0.03 ms |
| 背景填充 + 4 路缩放 | 约 0.13-0.14 ms |
| 背景填充 + 4 路缩放 + 高亮 | 约 0.95 ms |
| 背景填充 + 4 路缩放 + 文字 | 约 0.14-0.15 ms |
| 全部启用 | 约 0.97 ms |

各项增量耗时通过相邻对照组相减获得，因此可能存在约 0.01 ms 的测量波动。

## Y-only 高亮优化历史结果

新增的 `mix_yuv_benchmark` 使用相同四路输入、布局、高亮和 OSD 配置，执行
10 次预热后测量 1000 次调用并报告中位数。它不注册为 CTest，避免把机器相关的
时间阈值混入正确性测试。

同一台 macOS arm64 机器、同一套 Release 静态依赖构建的结果如下：

| 实现 | 完整 `MixYuv` 中位耗时 |
| --- | ---: |
| 优化前整帧 mask | 0.963-0.969 ms |
| 优化后 Y-only 四窄带 | 0.149 ms |

优化后 5 次独立运行的中位数分别为 0.162、0.149、0.149、0.145 和
0.149 ms。以 0.963 ms 与 0.149 ms 对比，完整合流耗时降低约 84.5%，
吞吐性能约提升 6.5 倍。结果达到本次优化设定的 0.30 ms 以下目标。

## 首次调用

以下首次调用数据来自优化前的整帧 mask 实现，用于保留历史基线。

稳定态测试会复用 `MixYuvContext`，字形和缓冲区已经进入缓存。测试用例中的
单次调用还可能包含以下首次执行成本：

- 高亮 mask 首次分配。
- FreeType 字形首次加载、栅格化和缓存。
- libyuv CPU 路径初始化。
- 指令页、字体文件和数据页的冷缓存开销。

Release 构建的新进程首次调用实测约为 1.28-3.71 ms，随后复用同一个 context
时稳定在约 0.97 ms。首次调用受操作系统页缓存和 CPU 状态影响较大。

Debug 构建曾测得 15.272 ms。该构建只有 `-g`，没有编译优化，不能用于评估
发布版本性能。

## 优化前热点分析

当前主要热点是 `DrawHighlights`。一路 640x360 高亮在 1280x720 输出上会执行：

1. 清空整个高亮 mask，共 921,600 个元素。
2. 遍历整个 640x360 高亮 Rect，共 230,400 个像素，判断像素是否位于边框。
3. 再扫描整个 Y plane，共 921,600 个像素，根据 mask 写入高亮颜色。
4. 再扫描 640x360 个 UV 位置，每个位置读取对应的 4 个 Y mask 值并计算覆盖率。

即使实际边框只有约 4 像素宽，高亮实现仍会对整个输出执行多轮标量扫描，
因此高亮约占完整调用耗时的 85%。

其他操作：

- 4 路缩放由 `libyuv::I420Scale` 完成。当前场景是 1280x720 到 640x360
  的精确二分之一缩放，libyuv 的 SIMD 路径耗时较低。
- FreeType 字形缓存在 `MixYuvContext` 中。稳定态主要执行少量字形位图的 Y plane
  混合，耗时约占 1%。
- 背景填充需要写入约 1.38 MB 的 I420 数据，但在 Release 下只占约 3%。

## Y-only 高亮路径

第一版优化只修改 Y plane，U/V plane 保持 source 合流后的原值。彩色高亮因此
变为亮度高亮。这一实现取得了最低 CPU 开销，但后续产物检查发现该视觉取舍会
导致高亮辨识度明显下降，因此已被下文的彩色窄带实现替代。

每个高亮 Rect 仍使用原有边框宽度、内外各半和输出边缘裁剪规则，但边框被拆成
上、下、左、右四条互不重叠的窄带。每条窄带逐行执行连续 `std::fill_n`：

1. 不再分配、清零或扫描输出尺寸的 mask。
2. 不再扫描完整 Y plane。
3. 不再扫描或混合 U/V plane。
4. 高亮工作量由输出面积改为与实际边框面积成正比。
5. 多个高亮重叠时只会重复写相同的 Y 常量，不需要并集或去重状态。

## 高亮可见性回归调查

四路集成场景的第一路为红色 source，目标区域位于输出左上角。对优化前后 YUV
产物使用同一 FFmpeg RGB 解码路径采样，结果如下：

| 位置 | RGB 采样值 | 视觉效果 |
| --- | ---: | --- |
| source 内部 | `(231, 0, 1)` | 红色 |
| Y-only 边框 | `(255, 66, 94)` | 与 source 同色系的浅红/粉色 |
| 原彩色边框 | `(0, 228, 116)` | 与 source 色相差异明显的绿色 |

问题不是高亮开关或边框几何失效。Y-only 实现仍写入 `Y=143`，但保留 source 的
`U=102/V=240`，所以边框继续继承红色色相。边框总宽度为 4 px，同时第一路贴合
画布上边和左边，向外的 2 px 会被裁剪，这两条边实际仅剩向内的 2 px。窄边框和
同色系颜色共同造成了“基本看不到高亮”的结果。

原测试只断言高亮位置的 Y 值为 143，并明确断言 U/V 不变。它能证明边框写入和
几何正确，但不能验证高亮与 source 的颜色对比度，因此没有拦截这次视觉回归。

## 彩色窄带修复

修复保留 mask-free 四窄带 Y 绘制，并只处理实际受边框影响的 I420 chroma
采样点：

1. Y plane 继续使用原有四窄带写入 `Y=143`。
2. 将边框映射到 U/V 的 2x2 luma 采样网格，仍拆分为不重叠的上、下、左、右
   四个 chroma 窄带，不扫描 Rect 内部或完整 UV plane。
3. 对每个 chroma 采样点统计其 4 个 luma 像素中属于所有高亮边框并集的数量。
4. 按覆盖率将固定 `U=113/V=35` 与原 chroma 混合；完全覆盖时直接得到固定
   高亮色，部分覆盖时避免奇数边界产生额外色度外溢。
5. 多个高亮重叠时，由最早覆盖该 chroma 采样点的 Rect 负责一次混合，并基于
   所有 Rect 计算并集覆盖率，避免重复混合。
6. 不分配高亮 mask 或其他动态缓冲，错误校验仍在首次写入前全部完成。

设 chroma 候选总数为 `P`、高亮 Rect 数为 `H`，并集覆盖检查的复杂度为
`O(P*H)`。当前四路目标场景最多 4 个高亮 Rect，`H` 很小；如果未来把该接口用于
大量同时高亮的 Rect，需要重新评估几何预计算或复用 scratch storage。

在 640x360 左上角高亮场景中，彩色实现约写入 5,988 个 Y 像素并处理 1,497 个
chroma 采样点。工作量仍与边框周长相关，而不是与 1280x720 输出面积相关。

### 彩色窄带微基准

由于当前工作区没有可用的 libyuv 构建包，且外部依赖源不可达，本次无法重新链接
并执行完整 `mix_yuv_benchmark`。为隔离本次新增 chroma 路径的成本，使用同一
Release 编译参数 `-O3 -DNDEBUG`，对一个 1280x720 输出中的 640x360 高亮执行
10 次预热和 1000 次测量。5 次独立进程结果的中位数如下：

| 高亮实现 | `DrawHighlights` 中位耗时 |
| --- | ---: |
| Y-only 四窄带 | 0.0022 ms |
| 彩色 YUV 四窄带 | 0.0378 ms |
| 彩色路径增量 | 约 0.0356 ms |

Y-only 的 5 次结果为 0.002209、0.002208、0.002208、0.002125 和 0.002125 ms；
彩色路径为 0.062041、0.040583、0.037792、0.037750 和 0.037709 ms。表中采用
5 次独立进程中位数，避免首次进程冷态波动影响结论。

对应的可复现入口为 `i420_highlight_benchmark`，它与机器相关的时间阈值一样不注册
为 CTest。使用固定依赖包配置 Release build 后运行：

```sh
cmake --build build-release --target i420_highlight_benchmark
./build-release/tests/i420_highlight_benchmark
```

该隔离结果不能替代完整 `MixYuv` 数据，但证明新增 chroma 处理没有重新引入旧实现
约 0.82 ms 的整帧 mask 热点。发布前应在具备固定静态依赖包的相同 Release 环境
中重新执行完整 benchmark，并将结果与历史 0.149 ms Y-only 数据分开记录。

## 后续优化优先级

1. 彩色高亮仍保持周长级四窄带实现，不再是主要热点；完整链路耗时需要在发布构建
   环境中复测。
2. 如果布局可以证明完全覆盖输出，可考虑跳过会被后续 source 全部覆盖的背景填充。
   该项收益约为 3%，优先级较低。
3. 当前缩放和文字绘制不是主要瓶颈，不建议在没有新性能数据的情况下优先改动。

## 结论

历史 Y-only 实现将四路 720p 合流的本机 Release 稳定态由约 0.97 ms 降至约
0.15 ms，但固定亮度和 source chroma 的组合无法保证高亮可辨识。当前彩色窄带
实现恢复固定高亮色，同时继续避免整帧 mask 和 Y/UV 扫描。隔离测试显示 chroma
修复增加约 0.0356 ms；完整调用仍需在固定依赖的 Release 环境中复测。所有绝对
耗时仅代表上述 macOS arm64 环境，其他架构需要独立测量。
